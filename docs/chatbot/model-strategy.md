# Chatbot Model Strategy

## Purpose

This document records the model direction for ONTHEBLOCK `ai-chatbot-service`.

The chatbot LLM is not the recommendation engine. It is a narrow response
generation model that explains already-grounded recommendation facts in polite
Korean.

## Core Decision

For MVP, do not train or fine-tune the open LLM. Use a small or medium
instruction model as a grounded response writer behind Hugging Face Inference
Endpoint/TGI.

The model should be selected with open LLM leaderboards, such as
`https://onyx.app/open-llm-leaderboard`, as one input. Broad reasoning, coding,
math, and long-context scores are not the main decision criteria for this
service.

The service domain is narrow:

- place
- price
- flavor
- drinks
- scent
- recommendation explanation
- profile or insufficient-data explanation

Because recommendation-service already provides ranked facts, the chatbot does
not need a very large reasoning model or a large token budget for MVP.

Initial MVP model:

```text
CHATBOT_LLM_MODEL=Qwen/Qwen2.5-7B-Instruct
```

Alternatives such as `Qwen/Qwen3-8B` or
`meta-llama/Meta-Llama-3.1-8B-Instruct` can be evaluated later. The first
deployment should optimize for stable short Korean answers, latency, and cost,
not broad reasoning benchmarks.

## Responsibility Split

| Component | Owns | Must Not Do |
|---|---|---|
| `recommendation-service` | Ranking, candidates, scores, reason codes, profile status, place/price/flavor/drink/scent facts | Generate user-facing prose |
| `ai-chatbot-service` | Intent handling, guardrails, prompt/context assembly, storage, response cards, source tracing | Rank or invent recommendation facts |
| Hugging Face OpenLLM | Polite Korean natural-language response from supplied facts | Invent facts, reorder candidates, create new recommendations |

## Model Selection Criteria

Prefer a model that is:

- strong enough for Korean instruction following
- stable at low temperature
- efficient enough for production latency and cost
- small enough to deploy and iterate on Hugging Face
- compatible with Hugging Face Text Generation Inference or an
  OpenAI-compatible `/v1/chat/completions` endpoint
- permissively licensed for the project use case

Leaderboard scores are useful for narrowing candidates, but final selection
should be based on ONTHEBLOCK evaluation cases.

## Token Budget Direction

Keep context compact.

The prompt should include only:

- user message
- classified intent
- profile status summary
- ranked recommendation candidates
- source IDs and reason codes needed for traceability
- missing facts when relevant
- strict no-invention instructions

Do not include raw survey answers, full conversation history, unrelated app
state, or large retrieved documents.

Initial target:

```text
input context: compact structured JSON
output: short polite Korean answer
max output tokens: about 256-512
temperature: about 0.2
```

These values can change after latency and answer-quality evaluation.

## Training Data Direction

Training is explicitly out of scope for MVP. After consent, retention, deletion,
PII filtering, and train/eval policy are approved, future training/evaluation
sources may include:

- user message
- assistant output
- intent
- profile status
- recommendation request IDs
- ranked candidate summaries
- reason codes
- missing facts
- feedback events

Do not train directly on:

- auth tokens
- secrets
- raw survey answers as canonical truth
- canonical map/place/menu/inventory database rows
- private data that is not needed for response generation

Before model training from production logs, finalize:

- user consent policy
- retention period
- deletion/export policy
- PII filtering
- train/eval split rules

## Deployment Contract

The chatbot service should call the deployed Hugging Face model through:

```text
CHATBOT_LLM_PROVIDER=huggingface_tgi
CHATBOT_LLM_ENDPOINT_URL=https://<endpoint>/v1/chat/completions
CHATBOT_LLM_MODEL=<model-id-or-endpoint-model-name>
CHATBOT_LLM_API_KEY_ENV=HF_TOKEN
```

The Hugging Face token must come from environment variables only.

## Evaluation Plan

Evaluate candidate base models and future fine-tuned checkpoints on
ONTHEBLOCK-specific cases, not only public leaderboards.

Required evaluation sets:

- `golden_cases.yaml`: normal grounded recommendation responses
- `no_answer_cases.yaml`: missing profile, missing location, no candidates,
  stale or low-confidence data
- `out_of_scope_cases.yaml`: unrelated questions and requests to invent data
- `ranking_integrity_cases.yaml`: answers must preserve recommendation-service
  order and must not add candidates
- `korean_tone_cases.yaml`: concise polite Korean output

Release gate:

- no invented place, drink, price, distance, inventory, flavor, or scent facts
- no candidate reordering
- no user ID accepted from chatbot request body
- no answer when evidence is missing
- card/source metadata generated by code, not by the model
- latency and cost acceptable for modal chatbot UX

## Implementation Plan

1. Keep the current provider abstraction and Hugging Face/TGI-compatible adapter.
2. Keep recommendation-service as the only ranking source.
3. Make prompt context compact and deterministic.
4. Add evaluation fixtures for grounded, no-answer, out-of-scope, ranking, and
   Korean tone cases.
5. Add an offline model-evaluation script that can call a configured Hugging
   Face endpoint and compare outputs against the fixture policy.
6. Store chatbot input/output and trace metadata in PostgreSQL, but block
   training use until consent and retention policy is approved.
7. Configure the Hugging Face Inference Endpoint/TGI env vars and run smoke
   tests against the real endpoint.
8. Compare candidate checkpoints using app-specific eval pass rate, latency,
   output length, refusal quality, and grounding violations.
